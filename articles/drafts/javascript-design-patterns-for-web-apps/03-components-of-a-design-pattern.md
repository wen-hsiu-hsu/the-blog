# 設計模式的六個組成：從名稱、情境到過度設計與反模式

> 延續 [[blog/courses_notes/javascript-design-patterns-for-web-apps/02-what-are-design-patterns|設計模式是什麼]]，上一篇把設計模式比喻成解決問題的食譜，這篇拆開來看一份食譜裡到底寫了哪些東西。

## 一個設計模式由六個部分組成

- **名稱**：用來建立共同語彙。說「這裡要用 singleton」，大家就知道在講什麼，不用再解釋做法
- **問題**：這個模式想解決的問題。套用之前，要先確認自己真的有這個問題
- **解法**：說明要解決這個問題，可以怎麼做
- **情境**：同一個問題在不同情境下，不一定該用同樣的方式解決。情境描述的是「在什麼樣的條件下，才該用這個解法處理這個問題」
- **後果**：套用設計模式不會只有好處，正面與負面的影響都會跟著出現
- **範例**：通常會用某一種程式語言寫出範例

範例這一項要特別留意語言差異。Java 和 C# 雖然各有不同，但在設計模式這件事上幾乎可以視為同一回事；換成 JavaScript 就完全是另一回事了。這也是上一篇提到 JavaScript 不是嚴格物件導向語言的延伸，同一份範例搬過來未必適用。

## 為什麼 Vanilla JS 專案需要設計模式

Vanilla JavaScript 給了完全的自由，這是優點，也是挑戰。

做過 Vanilla JavaScript 專案的人，大概都經歷過這個過程：一開始很簡單，能動、速度也快。接著開始加功能、加想法，問題就一個個冒出來，最後變成義大利麵式的程式碼（spaghetti code），專案裡很多部分全都耦合在同一段程式碼裡。

走到這一步，常會開始後悔：早知道就用個函式庫，React、Angular、Vue 或 Next.js 都好。不過理解一些設計模式之後，就能把這些函式庫和框架裡的想法，同樣用在 Vanilla JavaScript 上。

### 設定準則帶來的好處

重點在於替專案設定準則（guideline），它能改善：

- **可重用性**：程式碼更容易重複使用
- **可擴充性**：功能越加越多時，專案不會變成難以管理的怪物
- **一致性**：沒有準則、不遵守規則的話，web app 的每個功能都可能用上不同的模式、不同的寫法
- **效率**：主要指開發者體驗，開發起來更有效率；有時候也包括 web app 執行時的效能
- **除錯**：沒有遵循準則、沒用設計模式的 Vanilla JavaScript 專案，除錯起來可能很麻煩

## 任何人都能創造設計模式

設計模式沒有官方組織來認證哪些才算數，它完全由社群推動，說穿了就是一些解決問題的想法。

想創造一個設計模式，通常從一篇部落格文章開始：取個名字，說明在開發 app 時遇到了什麼問題，再提出解法、附上程式碼範例，然後發表出去。

很可能沒有人喜歡這個模式。但也可能社群覺得這是好主意，開始拿來實作，隔年就有人在研討會上講這個模式。設計模式的生命週期，就是這樣開始的。

## 不要因為聽起來很酷就用設計模式

這是整個主題裡最重要的一點：不要因為設計模式聽起來很酷、或是大家都在用，就拿來用。

決定使用某個設計模式之前，先確認兩件事：

1. 專案裡真的有這個模式要解決的問題
2. 專案的狀況符合這個模式定義的情境

兩者都不符合還硬套，等於在原本的問題上再加更多問題。不存在一份「每個專案都該用的 15 個設計模式」清單，每個專案、每個問題都要坐下來想清楚，再決定用哪個模式解決。

## 使用設計模式常見的失敗

大部分設計模式都會在程式碼上多加一層抽象，代表更多檔案、更多元件、更多 class，整體程式碼也會變多，累積到某個程度就會變成過度設計。常見的失敗有這幾種：

- **過度設計（over-engineering）**：抽象層一層層疊上去，最後超出實際需要
- **誤用**：套用的設計模式根本不是針對目前的問題，沒有解決任何事
- **僵化**：把設計模式當成必須遵守的法律，忘了它只是一份食譜。照食譜做菜時，覺得哪裡不對可以自己調整，食譜寫六顆蛋，改成四顆也可以，結果可能變好也可能變差，但本來就有調整的彈性。只照文件寫的做，可能得到錯誤的解法
- **團隊的學習曲線**：團隊成員不懂設計模式就得另外學，不過換成導入函式庫也一樣要學
- **複雜度**：套用設計模式會讓專案變得更複雜，有利也有弊
- **效能負擔**：元件更多、要載入的檔案更多、要在記憶體裡實例化的 class 也更多

效能負擔的影響要看情況。很多時候根本不是問題，有時候卻會造成影響。如果開發的是要跟硬體即時溝通的應用程式，大概會盡量少用這類設計模式；不過一般 web app 通常不是這種情況。

### 第一個專案就會感受到這種取捨

之後的第一個專案會從非常簡單的版本開始，完全不用設計模式，很好理解，但看得出它的問題在哪。接著套上設計模式，行為一樣，可擴充性等好處都有了，卻也可能讓人覺得已經過度設計了。

所以要找到平衡點，也就是自己覺得套用更多設計模式還算舒服的那個程度。

## 什麼是反模式

反模式（anti-pattern）指的是一種做法，可能是設計模式、食譜或某種解法，一開始看起來有好處，最後卻帶來不好的結果。

聽到有人說「這是反模式，不要這樣做」，意思就是：這個做法感覺能帶來一些好處，但實際上沒有。所以要盡量避開反模式。

## 很多人早就在用設計模式，只是叫不出名字

寫 JavaScript web app 一段時間的人，多半已經認識不少設計模式，只是一開始沒認出來。

例如曾經用某種固定格式建立物件，看了設計模式之後才發現：「原來我寫的是 factory。」以前不知道名字，但已經在用這個想法了，因為設計模式本來就只是一個想法。現在有了名字，跟同事討論時就能直接說「我在這裡用了 factory」。

我自己就常有這種感覺，寫著寫著覺得好像用了某個 design pattern，只是叫不出名字。

## 複習

### 構成一個設計模式的六個組成是什麼？

名稱（建立共同語彙）、問題（這個模式想解決的問題）、解法（說明怎麼解決問題）、情境（什麼時候該用這個解法）、後果（正面或負面的影響），以及範例（通常用某一種程式語言寫成）。

### 實作設計模式之前，最重要的原則是什麼？

先確認專案裡真的有這個設計模式要解決的問題，而且符合這個模式定義的情境，再決定要不要使用。不要因為聽起來很酷或大家都在用，就拿來用。

### 使用設計模式時，常見的三種失敗是什麼？

過度設計（加了太多抽象層、檔案、元件和 class）、誤用（套用的設計模式沒有解決實際的問題），以及僵化（把設計模式當成嚴格的法律，而不是可以調整的食譜）。

### 什麼是反模式？

反模式是一種做法、食譜或解法，一開始看起來有好處，最後卻帶來不好的結果。某個做法被稱為反模式，意思是它看似有優點，實際上沒有。

### 在 Vanilla JavaScript 專案中使用設計模式有什麼好處？

提升程式碼的可重用性、功能變多時有更好的可擴充性、web app 各部分保持一致、開發者體驗更有效率（有時也包含效能），以及更容易除錯。
